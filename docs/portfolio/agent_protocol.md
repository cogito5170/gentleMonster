# 혁주 작업 공간 ↔ 분석 · 편집 세션 전달 규약 (ga-SDK 형식)

메시지 형식은 [cogito5170/ga-sdk](https://github.com/cogito5170/ga-sdk)(브랜치 `claude/CMD-GA57`)를 따른다.
- 사용하는 꼴: `ga/forms/kinds.py`, `ga/specs/forms/*.pspec`의 `directive/2`, `report/2`
- 메시지 모양(wire): `ga/forms/core.py`의 `dump_wire`

## 1. 역할

| 역할 | 세션 | 하는 일 |
|---|---|---|
| 허브 | 혁주 작업 공간 `session_01FYwvzhDCTYAAM1u37s5yGE` | 사용자 요구를 지시(`directive/2`)로 바꿔 보낸다. 보고(`report/2`)를 받아 사용자에게 결과만 보여 준다. 원고 파일 기록과 커밋을 맡는다. 글을 직접 분석하거나 고치지 않는다. |
| 분석 | Context Analysis Agent `session_01GGPjmZVBdKmygvWvYsFFv6` | 진단만 한다. 출력은 `context_flow_analysis/1`과, 편집 세션에 넘길 `semantic_edit_context/1`(original_text 채움)이다. |
| 편집 | Editor_Writer Agent `session_0122yxjinLCToP7QLnhJbJka` | `semantic_edit_context/1`을 받아 고친다. 출력은 `editor_writer_result/1`이다. |

```
사용자 → 허브 ─directive/2 CMD-HJn→ 분석 ─report/2→ 허브
          허브 ─directive/2 CMD-HJn+1 (after CMD-HJn)→ 편집 ─report/2→ 허브
사용자 ← 허브 (결과만)
```

- 분석 세션과 편집 세션은 서로 직접 주고받지 않는다.
- 허브는 분석 세션의 `semantic_edit_context/1`을 **고치지 않고** 편집 세션에 넘긴다.

## 2. 메시지 모양

- `send_message` 본문에는 ```` ```ga ```` 블록 하나만 넣는다. 블록 안은 줄바꿈 없이 이어 쓴 JSON 한 덩어리다.
- 블록 뒤에 꼬리 줄(`---` 다음 줄에 `_Generated by [Claude Code](https://claude.ai/code)_`)을 붙인다. 다른 글은 쓰지 않는다.
- 원고, 진단, 수정본처럼 긴 내용은 메시지에 넣지 않는다.
  - gentleMonster 저장소에 파일로 커밋한다.
  - 메시지에는 `refs` 또는 `items[].evidence`로 `저장소@브랜치@sha:경로`만 적는다.
- 지시 번호는 `CMD-HJ<n>`이다(`^CMD-[A-Z]+\d+$`).
- 사람용 메모(`note`)는 280자 이하다.

### 2-1. 허브 → 세션: `directive/2`
- 반드시 채우는 것: `id`, `rev`, `to`, `goal`, `why`, `scope`(S1…), `done_when`(D1…), `refs`(입력 파일)
- 편집 지시에는 `after: ["<분석 지시 id>"]`를 단다.
- 입력 파일 `docs/portfolio/handoff/CMD-HJ<n>.input.json`(`hj_handoff/1`)에 들어가는 것:
  - 원고 전문
  - 사용자 피드백 원문
  - 직무 설명
  - 사용자 규칙
  - 사용자가 거절한 소재
  - 사용자가 아직 정하지 않은 것

### 2-2. 세션 → 허브: `report/2`
- `from`, `handled`(`status`: done · paused · declined)
- `items`(D1…, `state`: met · unmet · blocked · na, `evidence`에 결과 파일 경로)
- `commits`(`{repo, branch, sha}`)
- 막히면 `blockers`(`kind`: env · permission · credential · budget · dependency · design)를 쓴다. 사용자 판단이 필요하면 `design`이다.
- 결과 파일은 각 세션 자기 브랜치의 `docs/portfolio/handoff/CMD-HJ<n>.result.json`에 둔다.

## 3. 요구 종류별 경로

| 사용자 요구 | 경로 |
|---|---|
| "작성해 줘"(새로 쓰기 · 다시 쓰기) | 분석(문법 · 5유형 × 5페르소나 설계) → 편집(5케이스 집필) → 허브가 5케이스를 보여 주고 사용자가 고름 (§6) |
| "흐름 봐 줘", "어디가 어색해?" | 분석 |
| "고쳐 줘", "문맥 이어지게" | 분석 → 편집 |
| "대안 문장 n개" | 편집 (분석 생략, `semantic_edit_context/1`은 허브가 해당 문장 범위로 채움) |
| "n안 채택" | 허브가 원고에 반영 (세션 호출 없음) |

## 4. 사용자 규칙 (입력 파일 `user_rules`, `rejected_by_user`에 매번 넣는다)

- 사실 · 경험 · 성과 · 동기 · 감정은 지어내지 않는다.
- 합니다체로 쓴다. 지칭어(저는 · 제가 · 저를)는 쓰지 않는다.
- 추상적이거나 감정적인 표현은 피한다.
- 통째로 다시 쓰지 않는다. 부분만 고치고 대안을 준다. 고르는 것은 사용자다.
- 문항별 글자 수 제한은 공백 · 줄바꿈 포함 `len()`으로 센다.

## 5. 허브가 사용자에게 보여 주는 것

- 결과만 보여 준다.
  - 진단 요약
  - 고친 문장의 전 · 후
  - 대안
  - 글자 수
  - 사용자가 골라야 할 것
- 지시와 보고의 원문은 `docs/portfolio/handoff/`에 남기고, 진행 과정은 보여 주지 않는다.
- 세션이 `blockers`(design)를 보내면 그 질문만 짧게 전한다.

## 6. 5케이스 선택 방식 (작성 요구의 기본값)

새로 쓰거나 다시 쓰는 요구에는 완성본 하나가 아니라 **케이스 5개**를 보여 주고, 사용자가 고른다.

1. 분석 세션이 세 가지를 정한다(`writing_grammar/1`, `persona_brief/1`).
   - 자기소개서 문법(G1…)
   - 글의 종류 5개
   - 페르소나 5개
2. 편집 세션은 케이스 5개(C1…C5)를 쓴다.
   - 케이스마다 문항 글자 수 제한 안에서 쓴다.
   - 사실은 모두 같고, 무엇을 앞세우고 어떤 순서 · 목소리로 쓰는지만 다르다.
3. 허브가 보여 주는 것:
   - 케이스별 한 줄 요약(유형 · 페르소나 · 무엇을 앞세웠는지)
   - 전문과 글자 수
   - 문법 점검표
4. 사용자가 고른 것은 `docs/portfolio/handoff/selection.json`에 적는다.
   - 기록할 것: 문항, 고른 케이스, 섞을 부분
   - 이후 다듬기는 고른 케이스를 원고로 삼는다.
5. 섞어 달라는 요구(예: "C2 구조에 C4 강점 셋째")가 오면, 고른 부분만 편집 세션에 넘긴다.
