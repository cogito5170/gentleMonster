# 기억과 맥락 — 무엇을 기억하고, 모델에 무엇을 보이나

`!젠몬` 이 대화를 이어 갈 수 있게 하면서, **모델이 앞서 한 말이 사실처럼 되돌아오지 않게** 한 구조다.
저장(`memory.jsonl`, 전부 남긴다)과 모델 입력(`context.build`, 매 요청마다 고른다)을 가른다.

## 1. 진단 — 바꾸기 전 (`4eb4ffa`)

**gentleMonster 자체에는 대화 기억이 없었다.** 모델 입력은 한 곳에서만 지어졌다:
`synopsis.prompt(brief)` (브리프 한 줄 + 규칙 + 예제 JSON). 재시도는 같은 기본 프롬프트에 직전 답과
코드가 잰 문제를 붙여 다시 짓는다(누적되지 않는다). 기억·요약·검색은 없었다. 그래서 문제는 "기억이 쌓여 틀린다"
가 아니라 **정정이 모델에 닿지 않는다** 였다:

| 경로 (옛 `intent.py`) | 일어난 일 | 근거 |
|---|---|---|
| `!젠몬 방금 거 벽은 나무로 바꿔` | `"바꿔"` 가 layout 단어라 **무드보드 재빌드** — 모델 호출 없음, job 그대로 | `intent.py:37`, `:109` |
| `!젠몬 방금 거 입구 조명 어둡게` | 단계 단어도 layout 단어도 없어 **status** 답 — 요청이 버려짐 | `intent.py:110` |
| `!젠몬 아니, 벽은 콘크리트 말고 나무로 해줘` | 작업 지칭이 없고 길이가 12자 이상이라 **새 작업 make** — 앞의 브리프·제약을 전부 잃는다 | `intent.py:111` |

eval 의 `before` 열이 이 경로를 옛 코드 그대로 돌려 보인다(S1: 정정 턴 → `make`, 최종 요청 → `layout`, 모델 호출 0).

**기억을 붙이는 흔한 길이 다음 병이다.** 이 봇의 호스트(se_new)가 이미 그 꼴이다 — 바꾸지 않았고 진단만 적는다:

- `discord_bot_server.py:256` `MemorySaver()` — 스레드의 대화 전체가 매번 모델에 간다. 40줄이 넘으면 `compact.py` 가 간추린다.
- `compact.py:66,90` — 간추림 노트에 **모델의 마지막 답 머리**를 그대로 적는다.
- `agent_memory.py:136–165` `search_memory` — 노트를 단어 수로 점수 매겨 돌려준다. 누가 한 말인지(사용자/모델), 아직 유효한지 구분이 없다.
  그래서 모델이 한 번 틀리게 답한 것("폭 24m 로 확정")이 노트로 남고, 다음 검색에서 사실처럼 돌아온다.

## 2. 조사 — 이 문제는 무엇인가

| 연구 | 이 구조에 준 것 | 확인 수준 |
|---|---|---|
| Laban et al. 2025, *LLMs Get Lost In Multi-Turn Conversation* ([arXiv:2505.06120](https://arxiv.org/abs/2505.06120)) | 다중 턴에서 평균 39% 하락, 대부분 신뢰성 저하. 모델이 이른 가정을 세우고 **자기 앞 답에 기대며** 회복하지 못한다 → 모델 답을 기억에서 "미검증" 으로 격하 | [출처:초록] |
| Zhang et al. 2023, *How LM Hallucinations Can Snowball* ([arXiv:2305.13534](https://arxiv.org/abs/2305.13534)) | 앞의 실수에 과잉 확약 → 더 많은 실수. 따로 보이면 자기 오류의 67–87% 를 알아본다 → 검증은 **따로** 한다 | [출처:초록] |
| Liu et al., *Lost in the Middle*, TACL 2024 ([doi:10.1162/tacl_a_00638](https://aclanthology.org/2024.tacl-1.9/)) | 긴 입력 가운데의 정보를 덜 쓴다 → 창(1M)이 아니라 작은 작업 한도(12k), 지시·정정을 맨 앞에 | [출처:초록] |
| Dhuliawala et al., *Chain-of-Verification*, Findings ACL 2024 ([arXiv:2309.11495](https://arxiv.org/abs/2309.11495)) | 검증 질문을 초안과 떼어 답하면 덜 베낀다 → `verify.model_check` 는 질문·원자료·주장만 본다 | [출처:초록] (factored 변형이 가장 낫다는 말은 2차 출처) |
| Zep / Graphiti ([arXiv:2501.13956](https://arxiv.org/abs/2501.13956)) | 모순되는 새 사실이 오면 옛 간선을 지우지 않고 무효화(이력 보존) → `superseded` + 양방향 링크 | [출처:조각] (invalid_at 세부는 2차 출처) |
| LongMemEval, ICLR 2025 ([arXiv:2410.10813](https://arxiv.org/abs/2410.10813)) | 장기 기억 평가 축에 knowledge update · abstention 이 있다 → eval 의 S1/S3(갱신) · S5(근거 없음) | [출처:초록] |

**가중치 수준과 애플리케이션 수준을 가른다.** 이른 가정·자기 답에 대한 과잉 확약은 모델의 성향이다(가중치 수준 —
여기서 못 고친다). 이 저장소가 고칠 수 있는 것은 **그 성향이 먹이를 얻는 경로**다: 무엇을 입력에 넣고, 어떤 표지를
붙이고, 무엇을 빼는가. 이 변경은 전부 후자다.

**도입하지 않은 것.** LangChain/LangGraph(이 패키지는 의존성이 표준 라이브러리 + 렌더 도구뿐이고, 필요한 것은
기록 하나와 고르는 함수 하나다), 벡터 DB(작업 하나의 기억은 수십~수백 줄이라 선형 훑기로 충분하고, **유사도는
그 말이 아직 유효한지 말해 주지 않는다** — 유효성은 `kind` 와 `status` 가 정한다).

## 3. 구조

```
!젠몬 방금 거 벽은 콘크리트 말고 나무로
  intent.parse ──────────── revise (전에는 layout/status/make 로 흩어졌다)
  discord_cmd ───────────── 정정 범위가 불분명하면 여기서 되묻고 끝 (아무것도 안 띄우고, 아무것도 안 덮는다)
  python -m gentle_monster revise <job> "<말>"
    pipeline.revise
      memory.Store.ingest_user   턴 기록 · 슬롯 추출 · 같은 슬롯의 옛 사용자 말을 superseded 로
      context.job_facts          job.json 을 코드가 읽은 원자료 (모델이 job 에 대해 한 말이 아니다)
      context.build              예산 안에서 고르고 표지를 붙인다 + trace
      synopsis.generate(base=revise_prompt, checks=verify.problems)
                                 spec.check + 사용자 슬롯 코드 검사가 실패하면 그 사실을 들고 재시도
      _record_draft              새 초안 = model_inference (옛 초안은 superseded, job.v<n>.json 로 남김)
      verify.code_check / model_check  → synopsis.md "Checked against your instructions" + 보고
```

**기록** (`out/<job>/memory.jsonl`, append-only, git 밖):
`id · content · kind · source{type,ref} · key/value · turn · created_at · updated_at · status · supersedes/superseded_by · conflicts_with · evidence`.

| kind | 어디서 | 믿음 |
|---|---|---|
| `user_stated` | 사용자 턴 (`source.type` 이 `turn` 이 아니면 거부) | 높음 — 새 말이 옛 말을 대체 |
| `source_fact` | 코드가 파일에서 읽거나 잰 것 (`source.type == model` 이면 거부) | 높음 |
| `model_inference` | 모델 답 · 초안 · 설계 이유 · 번들 예제 · 모델 검증자의 판정 | 0 — 표지 "UNVERIFIED", 맨 뒤, 먼저 잘림 |
| `summary` | 다른 기록의 간추림, `sources` 를 지닌다 | 낮음 — 사용자/원자료와 모순되는 부분은 잘린다 |

- **승격**: `promote()` 는 모델 추론을 활성 사용자 진술이나 코드 측정을 근거로만 `source_fact` 로 올린다. 모델 검증자의
  "supported" 나 모델이 스스로 붙인 확신도(`confidence` 는 아예 저장하지 않는다)로는 안 된다.
- **정정**: 슬롯(brand · layout.W/D/H · room.floor/wall/ceiling/light · `def:<약어>`)은 정규식으로 읽는다. 같은 슬롯의
  새 사용자 말이 옛 것을 대체한다. "A 말고 B" 에서 A 가 가리킬 후보가 하나면 그것을 대체하고, **둘 이상이면 아무것도
  바꾸지 않고** `conflicts_with` 로 묶은 뒤 되묻는다. 다음 턴에 한쪽을 분명히 말하면 그 물음이 닫힌다.
- **잘라내기**: 아직 유효한 옛 턴 안에서 대체된 부분만 `⟨changed later, t5⟩` 로 바꾼다(턴의 다른 내용은 남는다).
  모델 답·요약 안에서 사용자 슬롯이나 job.json 과 모순되는 부분은 `⟨contradicted by m8⟩` 로 바꾸고, 자를 자리를
  모르면 그 기록을 뺀다.

**입력 조립** (`context.build`): 지시 → 정정 → 사용자가 정한 슬롯 → 미해결 충돌 → "기억에 없음" → 원자료 →
사용자 옛 말(최근 4턴, 요청과 단어를 공유하는 것, 공간에 대한 지시) → 모델의 옛 출력(관련된 것만, 미검증 표지).
앞의 다섯은 예산을 넘어도 자르지 않고(`over_budget` 로 표시), 뒤의 셋은 예산에서 잘린다. 예산 =
`min(창 − 출력 예약 8192, GM_CONTEXT_TOKENS=12000) − 고정 프롬프트`. 수정 프롬프트에는 예제 JSON 대신 현재 초안이
들어가고, 그 초안을 기억이 다시 말하는 줄은 "중복" 으로 뺀다.

**관측** (`out/<job>/context_trace.jsonl`, 요청당 한 줄): 고른 기록 id · 구획 · 이유, 뺀 기록 id · 이유, 잘라낸 슬롯,
원자료 ref, 구획별 토큰 추정, 예산, 모델의 usageMetadata 토큰 · 지연 · 시도 수. 대화 원문은 없다(지시는 12자 해시).
사람이 볼 때는 `python3 -m gentle_monster memory <작업> [--all]` · `!젠몬 기억`.

기준 1–6 모두 통과. **그러나 처음부터 통과한 것은 아니다:**

- 첫 실행에서 기준 2·3 이 **실패**했다. 둘 다 *측정* 쪽 결함이었고 문자열을 열어 확인한 뒤 측정을 고쳤다:
  (2) trace 검사가 revise **뒤**의 상태와 비교해, 요청 뒤에 새 초안이 대체한 옛 초안 기록을 "보이면 안 되는데 보였다" 로 셌다.
  (3) 내가 지은 잡담의 모델 답이 사용자 질문을 그대로 인용해서, 사용자 구획에 있는 사용자 문장을 "모델 주장" 으로 셌다.
  측정을 고친 것이므로 이 두 기준의 통과는 그만큼 덜 독립적이다.
- 같은 실행에서 S4 의 `after` 가 모델 잡담을 예산이 찰 때까지 담는 것을 보고(단위 테스트: 300턴에 4037 토큰), **시스템을**
  고쳤다 — 요청과 무관한 모델 출력은 뺀다.
- S6 에서는 요청이 요약과 단어를 공유하지 않아 요약이 "무관" 으로 빠지고, 잘라내기 경로가 시험되지 않았다. 그래서 첫 실행 뒤
  **S6b 를 더했다**(요청이 바닥·폭을 말한다). 더 어려운 쪽으로 더한 것이고, 기준 1 에 넣었다.

**토큰은 공짜가 아니다.** 짧은 대화(S1–S3, S5)에서는 `after` 가 `naive` 보다 150–220 토큰(6–10%) **많다** — 표지 붙은 구획과
job.json 원자료 줄 값이다. 줄어드는 것은 대화가 길거나 잡음이 섞일 때다(S6·S6b·S8: 3–10% 적다. S4: 160턴에서 12509 → 2476, 80% 감소, 턴 수가 늘어도 거의 일정).

**출력 수준(정정이 실제 답에 반영되나, 근거 없는 주장, 반복 변동, 비용·지연)은 재지 못했다.** 이 컨테이너에 Gemini 키가
없다. `--live --repeat N` 이 같은 입력을 Gemini 에 N 번 보내고 돌아온 job JSON 을 코드로 채점하도록 짜 두었지만,
돌리지 않은 것을 돌린 것처럼 적지 않는다.

## 5. 한계

- 슬롯 추출은 정규식이다. "벽면을 원목 느낌으로" 처럼 목록 밖의 표현은 슬롯이 안 되고 자유 문장으로만 남는다(그래도 기억에는
  남고 최근 턴·관련 턴으로 입력에 들어간다). 잘못 읽으면 코드 검사가 틀린 값을 강요한다 — 재료 단어가 표면 단어 **뒤**에
  올 때만 읽도록 좁혔다(`"거울 벽을 추가"` 는 슬롯이 아니다).
- "A 말고 B" 가 아닌 정정("그건 아니야, 다시")은 무엇을 대체하는지 모르므로 아무것도 대체하지 않는다.
- 관련성 판단은 단어 겹침이다. 같은 뜻의 다른 말은 못 잡는다 — 대신 최근 4턴과 "공간에 대한 지시" 는 겹침 없이도 들어간다.
- 토큰 수는 추정치다. 실제 수는 모델이 답할 때 trace 의 `llm.prompt_tokens` 에 남는다.
- 모델 검증자(`model_check`)도 모델이다. 그 판정은 보고만 하고 사실로 올리지 않는다. 반대로 "supported" 라고 해서 옳다는
  보장도 없다.
- se_new 쪽 경로(`MemorySaver`, `compact.py`, `search_memory`)는 진단만 했고 바꾸지 않았다.
