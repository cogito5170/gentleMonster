# context eval — 같은 사례, 세 가지 입력 조립

`python3 eval/context_eval.py` 는 아래 사례마다 **최종 요청 하나**에 대해 모델에 들어가는 입력을 세 가지 방식으로 짓고 잰다.

| 조건 | 무엇인가 |
|---|---|
| `before` | 이 변경 **전** 코드 그대로 (`git show 4eb4ffa:` 의 `intent.py` · `synopsis.py` 를 불러 쓴다). 그때의 `!젠몬` 은 대화 상태가 없었다: 후속 말은 `make`(새 작업) · `layout`(무드보드 재빌드) · `status` 로 갈렸고, 뒤의 둘은 **모델을 부르지 않는다** — 정정이 모델에 닿지 않는다. |
| `naive` | 흔한 "기억 붙이기": 대화 전체(사용자 + 모델 답)를 그대로 잇고, 키워드 검색 상위 5개 노트(요약 · 모델 답 포함, 상태 구분 없음)를 덧붙인다. se_new 의 `MemorySaver` + `compact.py`(마지막 답 머리를 노트로) + `agent_memory.search_memory` 와 같은 꼴. |
| `after` | 이 변경: `pipeline.revise` 를 **실제로 돌려** (가짜 모델이 프롬프트를 받아 적는다) 그 프롬프트를 잰다. |

세 조건 모두 같은 고정 프롬프트(수정 지시 + 현재 초안 JSON)를 쓰고, 다른 것은 **맥락 블록**뿐이다(`before` 는 그때의 프롬프트 그대로).

## 사례

| id | 필수 사례 | 내용 |
|---|---|---|
| S1 | 초기 사실을 나중에 정정 | t1 "벽은 노출 콘크리트로 마감" → t4 "아니, 벽은 콘크리트 말고 나무로" → 최종 요청은 다른 이야기(조명) |
| S2 | 모델의 과거 추론 ↔ 원자료 충돌 | 모델이 앞서 "폭 24m 라 30m 런웨이가 들어간다" 고 답했다. job.json 은 폭 20 m |
| S3 | 오래된 기억 ↔ 현재 지시 | t1 "조명은 어두운 갤러리로" → 최종 "이번엔 조명을 자연광으로 바꿔줘" |
| S4 | 관련 없는 대화가 길게 | t1 의 제약("벽은 석회로") 뒤에 실제 사용자 질문(data/user_questions 22–44, 포트폴리오 작업)과 답이 40 · 160 턴 |
| S5 | 근거가 없거나 검색 안 됨 | "지난번에 정한 색온도 그대로" — 어디에도 색온도가 없다 |
| S6 | 요약·검색 결과에 잘못된 과거 답 | 간추림 노트: "폭 24m, 바닥은 콘크리트로 확정" ↔ 사용자: 폭 20 m, 바닥 화강암 |
| S7 | 정정 범위 불명확 (추가) | 바닥·벽이 모두 콘크리트일 때 "콘크리트 말고 나무로" |
| S8 | 실제 대화 (추가) | Q25 "SPA = STYLIST, PHOTOGRAPHER, ARCHITECT" → Q34 "SPA (STYLE, PASSION, ARCHITECTURE)" (data/user_questions 원문) |

## 측정 (입력 수준 — 모델 호출 없이 결정적)

- **정정 반영(입력)**: 사례의 `in` 표지(정정된 값)가 입력에 있는가.
- **무효 기억 포함**: 사례의 `not_in` 표지(대체·반박된 문장)가 입력에 있는가. `after` 는 trace 의 제외 목록과도 맞춰 본다.
- **모델 주장이 사실처럼 들어감**: 모델 답·요약의 문장이 "UNVERIFIED" 구획 **밖**에 나타난 수.
- **입력 토큰**: 추정치(ASCII/4 + 그 밖의 글자 1개당 1; 오프라인 토크나이저가 없다). 세 조건에 같은 추정기.

## 측정 (출력 수준 — 모델 필요, `--live`)

같은 입력을 Gemini(`GEMINI_MODEL`, 기본 gemini-2.5-flash, temperature 0.9 = 운영값)에 `--repeat N` 번 보내고, 돌아온 job JSON 을 **코드로** 채점한다(LLM 심판 없음): 정정된 값이 출력에 있는가, 반박된 값(폭 24 m 등)이 출력에 있는가, S5 에서 색온도 값(예: 2700K)을 지어냈는가. 반복 간 표준편차 · 지연 · usageMetadata 토큰 · 비용(가격은 `GM_PRICE_IN` / `GM_PRICE_OUT` USD/1M, 기본값은 가정).

## 성공 기준 — 결과를 보기 전에 적는다 (이 파일은 첫 실행 전에 커밋된다)

입력 수준, `after`:

1. 정정 반영 100% — S1 · S3 · S6 · S8 의 `in` 표지가 모두 있다.
2. 무효 기억 포함 0 — 모든 사례에서 `not_in` 표지 0개, 그리고 대체된 기록 id 가 trace 에 "superseded"/"contradicted" 로 제외돼 있다.
3. 모델 주장이 사실 구획에 들어간 수 0.
4. S5 에는 "기억에 없음" 안내가 들어간다. S7 은 모델을 부르지 않고 되묻고, 아무 기록도 대체하지 않는다.
5. S4 (160 턴) 의 입력 토큰이 `naive` 의 50% 이하이고 예산 한도(12,000) 안이다. 40 → 160 턴으로 늘 때 `after` 토큰 증가 10% 이하.
6. 기존 테스트(tests/*.py)가 그대로 통과한다.

출력 수준(`--live`): `after` 의 정정 반영률이 `naive` · `before` 이상이고, 반박된 값 채택이 그 둘 이하. **이 컨테이너에는 Gemini 키가 없어 돌리지 못했다** — 돌린 것처럼 적지 않는다.

## 이 평가가 못 보는 것

- 입력 수준 지표는 *모델이 무엇을 보았나* 이지 *모델이 무엇을 했나* 가 아니다. 입력에서 무효 기억을 뺀 것이 출력에서 그 오류가 사라진다는 증명은 아니다 — 그건 `--live` 몫이다.
- 표지 문자열 검사는 표지를 고른 내 선택에 기댄다. 그래서 `after` 는 trace 의 id 단위 제외 목록과 이중으로 맞춘다.
- 사례는 내가 지었다(S8 · S4 의 잡담만 실제 대화). 슬롯 추출(정규식)이 못 읽는 표현은 이 사례들이 덮지 않는다.
